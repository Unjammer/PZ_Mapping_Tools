PZTools Unofficial user guide

This guide covers the functions added or restored on top of Tim Baker's WorldEd, TileZed and BuildingEd `basements` branches. It describes what each function does, where to find it, the data it expects, and the important limitations.

Supported development target: Windows 10, Qt 5.14.2, qmake, Qt Creator and MSVC 2017. A Qt 6 or C# migration is not part of this branch.

First start

  1. Extract the complete PZTools archive to a writable directory.
  2. Start WorldEd, TileZed or BuildingEd. The initial setup assistant opens automatically if no valid Tiles directory is detected.
  3. Leave Configuration catalogs on the packaged config directory unless you maintain a custom catalog set.
  4. Select the extracted Project Zomboid Tiles directory. PZTools also detects a directory named Tiles directly beside config.
  5. Confirm once. All three applications immediately share the paths.
config contains editable application data such as Tilesets.txt and BuildingTiles.txt. settings contains PZTools.ini, application INI files and logs. Deleting application INI files resets their preferences; shared paths remain in PZTools.ini. The directory must not be used as the configuration-catalog directory. See the configuration file reference and Build 42.20 checks before changing a catalogue manually.

Portable settings, layouts and logs

Why portable settings matter

The original applications used a mix of the Windows Registry, user-profile directories and application defaults. The current branch routes persistent state to local INI files so multiple PZTools installations can coexist with different tiles, themes and projects.

What is saved

  • main-window size, position and maximized state;
  • dock location, visibility and tab order;
  • the width of the left and right dock columns;
  • vertical sizes between dock groups;
  • horizontal and vertical QSplitter positions inside panels;
  • the visible tab whose geometry should be used when a dock group is tabbed;
  • theme, map paths, thumbnail preferences and feature-generation settings;
  • whether the previous editing session should be restored.

Layout state is also saved periodically. This makes a crash less likely to discard the latest panel arrangement. Hidden editing modes are prevented from overwriting a valid splitter state with zero-sized placeholders.

WorldEd reloads its complete tileset catalogue only when the effective Tiles directory changes. Confirming unrelated preferences does not rebuild the open maps and lots.

Resetting a broken layout

  1. Close the affected application.
  2. Make a backup of its INI file under settings.
  3. Remove only the layout/window groups from that INI, or rename the INI temporarily.
  4. Restart the application and arrange the panels again.

Logs

Logs live in the portable installation instead of a user-profile directory. A new UTF-8 file is created for each run, and the newest 20 files per application are retained. Lines contain severity, PID, thread ID and an optional worker name. They record selected paths, tileset loading, missing images, Building catalogs, Automapper diagnostics, WorldGen/loot loading, biomemap warnings, geometry repairs, and caught crashes.

Only the exact non-fatal libpng incorrect-sRGB-profile warning is omitted; other PNG warnings and errors remain visible. See Logs and useful issue reports for interpretation and a report checklist.

Changing shared paths

The initial setup assistant stores the catalog and extracted game Tiles paths in settings/PZTools.ini. The Tiles directory can also be changed from an editor's preferences or TileZed's Tilesets dialog. Restart open editors after changing a shared path so their catalogs are reloaded. Selecting 1x, 2x or custom directly is normalized automatically to the parent Tiles directory.

External QSS themes

Built-in themes are extracted as QSS files and external themes are discovered from themes. A QSS theme changes Qt widget styling only; it does not change map colors, tile images or project data.

Adding the Dark theme from an older fork

  1. Copy the old .qss file into the installation's themes directory.
  2. Restart the application so the theme list is rebuilt.
  3. Select the theme in Preferences.
  4. If an icon becomes unreadable, adjust its QSS foreground/background rules rather than editing application resources.

WorldEd, TileZed and BuildingEd resolve themes using the same portable location, but each application remembers its selection independently.

Legacy 300 and native 256 projects

The grid format belongs to the project. It is not inferred from the current zoom, thumbnail size or global settings.

Property300 × 300 Legacy256 × 256 Native
Cell size300 × 300 map squares256 × 256 map squares
Historical useOriginal WorldEd workflowDirect match for native 256 binary cells
LOT exportConverted to the game's 256 layout where requiredNo 300-to-256 cell conversion
Zombie samples30 × 30 per project cell32 × 32 per project cell
Project badge300 × 300 · LEGACY256 × 256 · NATIVE

For LOT generation, native means one-to-one. A WorldEd cell at project coordinate x,y produces exactly one x,y.lotheader and one world_x_y.lotpack, after the configured world origin is added once. The origin is never scaled from 300 to 256. Adjacent native TMX maps are placed every 256 squares, so no 44-square gap or partial extra output cell is introduced.

  • Each native cell TMX must be exactly 256 × 256.
  • Each output cell contains 32 × 32 chunks of 8 × 8 squares.
  • RoomDefs, objects, lots/static prefabs that cross a cell boundary, and chunkdata_X_Y.bin use the same 256-square geometry.
  • Legacy 300 projects continue to use the historical 300-to-256 converter.
Declaring a project Native does not resize an existing 300 × 300 TMX. Generate Lots rejects that cell and reports its coordinates, path, and actual dimensions. Convert or recreate the TMX explicitly.

Creating a native 256 project

  1. Use File > New World.
  2. Choose 256 × 256 (Native) in the grid-format field.
  3. Choose world width, height, tiles directory and destination normally.
  4. Save the PZW before adding TMX cells so paths and automations have a stable project location.
Changing the grid flag of an existing project is not a safe conversion. TMX dimensions, cell coordinates, roads, objects, thumbnails and generated files must all agree. Create a new project or use a dedicated converter.

TMX 2.0 is independent from the grid choice. A map without basements may have no negative levels even though the file format supports them.

Project Doctor: tiles and paths

Use WorldEd > Tools > Project Doctor: Tiles and Paths... when a project contains old paths, missing tiles, or files copied from several locations. Check project is read-only. Fix safely... creates a dated project backup before making any atomic replacement.

The normal result is a short table with Status, File, What this means, and What you can do. Clean files are grouped. Technical parser details remain hidden behind Show support details unless they are needed for a report.

  • TMX means a TileZed map; TBX means a BuildingEd building; PZW means the WorldEd project.
  • Missing or outside-project dependencies are reported and kept. The tool never guesses which Download/OneDrive/mod copy is correct.
  • Only unused and missing TMX sheet declarations are removed. Valid unused sheets stay in the complete legacy header.
  • Safe paths are resolved with the tools' normal readable 2x-first, then 1x/custom policy.
  • TBX lists are ID tables. BuildingEd rebuilds them and remaps every reference; direct XML list deletion is never used.

Read the complete Project Doctor safety, path, backup, and recovery reference before applying cleanup to a shared or legacy project.

WorldGen biome preview/editor and static prefabs

WorldEd exposes two separate windows after a saved map project is loaded: Tools > WorldGen Biome Editor / Preview... and Tools > WorldGen Prefab Editor.... The first resolves procedural/map biomes, weighted biome features, inheritance, and a representative 16x16-square preview. The second edits true z=0 static prefabs with the four runtime slots, a Tiles palette, strict TMX/TBX import, and staging.

  • The selected game WorldGen tree is always read-only.
  • Project definitions are saved under <map-project>/media/lua/server/WorldGen.
  • Selectors identify effective Game and Project provenance.
  • Biome features are probabilistic 1x1 through 8x8 patterns; they are not static prefabs.
  • The biome preview covers 2x2 game chunks. It is deterministic and representative, not a captured save.
  • Static prefabs apply at z=0 and contain only Floor, FloorFurniture, FloorOverlay, and Furniture.
  • JUMBO, JUMBOXL, and JUMBOXXL sprites retain their complete visual footprint; incompatible custom-sheet geometry is rejected explicitly.
The 8x8 chunk, 16x16 pending area, feature tiers, biome registries, and four prefab slots are confirmed against Build 42.20. The editor's 256x256 prefab cap, strict import failures, atomic writes, and refusal to write inside the game installation are tool safety policies.

Road generation is deliberately excluded while that runtime system is unfinished. Erosion is treated as a potential separate module. Authored-map replacement context, complete save-noise parity, and complete mod packaging are not claimed by the preview.

Read Build 42.20 WorldGen editor, biome preview, and prefabs before importing or staging a prefab.

Terrain and vegetation image editor

WorldEd includes a small Qt paint editor for the two source images used to create a map: ground in Map.png and vegetation in Map_veg.png. Open it from the WorldEd tools menu after loading a world project.

The menu command is disabled while no project is loaded. The editor needs the project's Rules.txt, grid format, bounds and map directory; creating a project-independent image would make those values ambiguous.

Create or open an image pair

  1. Load the destination PZW project.
  2. Open Terrain / Vegetation Image Editor....
  3. Choose 300 or 256 geometry from the project, then set the cell origin, width and height.
  4. Create blank ground/vegetation layers or open existing PNG files.
  5. Save the PNG pair and, when wanted, attach it to the current project.

The palette contains only colors declared by Rules.txt. Use the brush for normal painting, Fill for a contiguous region, the picker to recover a color from the image, and the vegetation eraser to restore an empty vegetation pixel. Zoom and the composite opacity control affect only the preview. Edits participate in Undo.

WorldEd estimates memory for the ground image, vegetation image and composite preview before allocating them. The default limit is 512 MiB. High-memory workstations can raise Terrain image memory limit in Preferences up to 64 GiB. Undo history requires additional memory, so use a value comfortably below the machine's available RAM.

Procedural generation

Terrain patches, vegetation, lakes, rivers and road networks are generated over the complete image rather than one cell at a time. A river or road can therefore cross a 300 × 300 or 256 × 256 cell boundary without a seam. Review the generated result, paint corrections, then save it as ordinary PNG files.

PNG dimensions must exactly match the chosen cell rectangle. Unknown palette colors are not silently approximated: the error identifies the color and its image coordinate. Very large allocations are rejected before creation, and saving uses an atomic replacement to protect an existing PNG.

WorldEd navigation and tile resolution

Project format badge

WorldView and CellView display the grid kind. Check this badge first when a thumbnail appears smaller than a cell, coordinates drift, or generated image dimensions are rejected.

Select all cells

Ctrl+A in WorldView selects all cells. Commands that work on the current selection, such as thumbnail regeneration or feature generation, can then process the entire world.

Open in TileZed

The context action starts the sibling TileZed.exe directly and passes the selected TMX path. It does not consult the system default application for .tmx. An explicit warning includes the expected executable path if TileZed cannot be found.

Consistent tile loading

WorldEd and TileZed now resolve tilesets through the same catalogs and wait for the tilesets required by a TMX. A red question-mark tile means the tile reference could not be resolved, not that the TMX geometry failed to open.

WorldEd thumbnails

What a thumbnail represents

A cell thumbnail is an isometric preview cached below the project's .pzeditor data. The minimap and WorldView use that cache; the Zombie Heatmap is a separate image and is not a map thumbnail.

Recreate thumbnails

  1. Select one or more cells in WorldView.
  2. Run the thumbnail recreate action for the selection.
  3. Watch the status/progress feedback while TileZed-compatible rendering data is loaded.
  4. If the result is blank, check the logs for missing tilesets or TMX errors.

The output resolution is configurable. Changing resolution changes preview detail and memory/disk usage; it does not change the project's 300/256 geometry. Grid color and thickness affect the editor overlay only.

Removing empty border cells

A PZW world is rectangular, even if only a few cells contain TMX files. Cell > Remove All Empty Border Cells... trims complete empty rows and columns from the outside of that rectangle.

Eligibility

A border cell must not contain identifiable map content. Cells with an existing TMX, objects or other protected data are retained. Interior holes are not removed because the PZW still has to describe a rectangle.

Result

  • world width and height shrink;
  • the world origin moves when the left or top border is removed;
  • roads and world-coordinate data are shifted to preserve their location;
  • the operation is grouped in Undo where supported.
Save a backup before changing the rectangle of a mature project. External scripts may have hard-coded the old origin.

Biomemap Generator

Open it with Tools > Generate Biome Map.... A biomemap is a data grid, not a decorative image. Input pixels must align exactly with project map squares.

Inputs and channels

InputContributionNotes
Map.pngBase biome sourceRequired.
Map_veg.pngVegetation contribution to biome classificationRequired; it is not copied as the output green channel.
Seven Biomemap Zone typesForaging-zone IDs in the output green channelRasterized from the current project.
Zone PNGAlternative exact green-channel IDsGrayscale or green-channel values; must match Map.png dimensions.

Zone-source choices

Rasterize zone objects reads only Vegitation, DeepForest, Forest, TownZone, Farm, FarmLand, and TrailerPark. These are the seven types that the game's metazoneHandler deliberately ignores in objects.lua because their data is expected in the Biomemap green channel. Read exact zone IDs from PNG supplies that same channel from an external image.

When zone objects are rasterized, Unzoned terrain fallback controls every pixel not covered by one of those seven objects. Automatic uses green 171 Vegitation only when WorldEd detects an active pixel 171 entry in the map's WorldGenOverride.lua. Otherwise it uses Vanilla-safe green 64 ForagingNav. The two exact values can also be selected explicitly. An external Zone PNG bypasses this setting because it supplies every green value.

Painting red biomes and green zones

Enable the Biomemap overlay and select the Biomemap painting tool. Its Paint control provides two independent modes:

ModeBrush unitChanged dataPreserved data
Biome (red channel)Individual map-square pixelsRed biome and ore selector IDGreen Zone, blue, and alpha
Zone (green channel)Complete 8 x 8 world chunksGreen foraging-zone IDRed Biome, blue, and alpha

The overlay changes to the active channel so green edits are visible. Each mode remembers its own ID and radius. A Zone radius of zero paints one complete chunk. Larger radii are measured in chunks. Dragging cannot leave partial or skipped chunks, and alignment follows absolute world coordinates for both Native256 and Legacy300 projects.

Do not move other WorldEd objects into the Biomemap. Vehicle zones, geometries, WorldGen, WaterZone, and every other vector zone/object type must still be exported through objects.lua. The generator excludes them from the image and reports the actual project types assigned to each path after generation.

In-game map stacking and Vanilla fallback

Project Zomboid loads the selected map folder together with the folders listed by its lots= entry. Biomemap files follow that same priority. If the selected mod map contains maps/biomemap_X_Y.png, that file is used for those exact coordinates. If it does not, the game can fall back to the matching file supplied by a lower-priority dependency such as Muldraugh, KY.

A biomemap file covers one complete 256 x 256 B42 tile. Supplying a modded file replaces both biome and foraging-channel data for that whole tile; it is not clipped to the mod's buildings or WorldEd zone shapes. Export every overlapping tile that needs different data, and omit a tile only when the Vanilla fallback is intentionally correct.

This is especially important for legacy 300 x 300 projects: their source bounds cross the B42 256-pixel boundaries. The generator aligns the source in world-square coordinates and always writes complete 256 x 256 files. Select the Vanilla maps directory as the optional base biomemap directory to preserve data in the uncovered parts of boundary files. Without a base file, those uncovered pixels use neutral ForagingNav data and are reported after generation.

The red channel stores biome IDs. The green channel stores foraging-zone IDs. File selection and Vanilla fallback happen for the complete 256 x 256 image; after that selection, the game requests zone values on its 8 x 8 chunk grid. It does not perform a second Vanilla fallback for uncovered chunks inside a selected mod image. The seven Biomemap-managed WorldEd zone types are an authoring source for the green channel; after generation, the game consumes those values from the exported PNG files. All other vector objects continue to come from objects.lua.

Dimension validation

The input must cover the project using its own cell size. A legacy project expects multiples of 300; a native project expects multiples of 256. The generator does not resize or pad source images because doing so would shift biome and zone data.

Warnings

Unknown source colors preserve their red byte and are listed. Invalid green-channel IDs stop generation. WorldEd types outside the seven Biomemap-managed zones are intentionally excluded from the image and listed as objects.lua types rather than reported as errors.

InGameMap feature generation

Generate Tree Features

Select cells, then use InGameMap > Generate Tree Features. Tree detection uses the exact tile names listed under Preferences > Feature Generation > Trees. The default catalogue includes the recognized classic vegetation trees, jumbo_tree_01_0, and the Build 42 species-specific Jumbo, XL, and XXL tree tiles.

Generate Road Features

Select cells, then use InGameMap > Generate Road Features. The generator derives polygons for primary, secondary and tertiary roads and railways from recognized map tiles. Trail generation from generic dirt tiles is disabled by default because those tiles can also represent bare ground, fields, construction areas or riverbeds. Enable it explicitly in Preferences only when the project uses those dirt tiles exclusively as paths. Squares covered by recognized water tiles or water tile properties are always excluded from inferred trails.

Before polygon conversion, each road-type mask closes isolated straight one-tile breaks and fills only small enclosed holes. Short disconnected fragments are discarded, while long narrow paths and sections continuing across a cell edge remain valid. Larger holes and genuinely separate roads remain separate so the cleanup does not merge distinct streets or erase intentional islands.

Separate settings are stored for normal roads, trails and railways because their shapes and expected precision differ. Defaults are deliberately conservative. Tile catalogues provide Add Tile, Remove Selected, and Restore Defaults controls. They are stored in the portable WorldEd INI. A padded tile ID such as blends_street_01_032 is accepted and normalized to the game-style name blends_street_01_32.

Polygon repair and export safety

Generated or manually edited geometry is normalized before XML or binary export. The exporter can remove duplicate closing vertices, consecutive duplicates and collinear points. It rejects shapes that cannot be represented safely.

Road polygons receive additional expanded triangulations at several map zoom levels in Build 42. Export safety therefore budgets all seven forms of each road polygon. A renderer-heavy cell is simplified conservatively. If it still exceeds the signed 16-bit index position, the exporter omits only the smallest internal road fragments required for safe XML and binary files. Source PZW features remain unchanged, and the portable log lists the affected cell and road classes.

Rejected conditionReason
Fewer than three distinct polygon verticesThe game renderer cannot fill a polygon without an area.
Zero-area or collinear polygonIt is geometrically a line, not a polygon.
Non-finite coordinateNaN and infinity cannot be serialized or rendered safely.
Coordinate outside signed 16-bit limitsThe binary/game representation would overflow.
Excessive properties or point complexityThe target binary format has bounded counts and indexes.

Logs identify the output, cell, feature index, feature properties and exact repair/rejection reason. Use these entries to locate source geometry that previously caused WorldMapRenderer$Drawer.fillPolygon() crashes.

Procedural loot viewer and editor

The same visual tool is available from TileZed > Tools > Procedural Loot Viewer / Editor... and BuildingEd > Building > Procedural Loot Viewer / Editor.... TileZed can focus the selected tile's container property; BuildingEd can focus the current room's internal RoomDef name.

  • Game Distribution_*.lua, Distributions.lua, and ProceduralDistributions.lua are read-only references.
  • RoomDef/container mappings and reusable procedural distributions show Game or Project provenance.
  • Direct items and junk show raw chance per roll. The neutral cumulative estimate is labelled as a preview, not an in-game guarantee.
  • Procedural rows expose relative weights, min/max, force selectors, and unresolved references.
  • Project output is written atomically below <project-or-mod>/media/lua/server/Items; output inside the selected game installation is rejected.

The editable JSON manifest and generated post-merge Lua are PZTools-owned output formats. They do not replace or rewrite the base-game registries. Vehicle distributions, item scripts, sandbox settings, and complete mod packaging remain out of scope. See the complete procedural loot reference.

Complete startup preload

TileZed and BuildingEd decode every available catalog tileset image during startup and keep the images in memory for the session. Maps, palettes and Lua scripts therefore see one stable, complete catalog without background image loading or asynchronous callbacks. The first window may take longer to become ready on a large Tiles installation; the progress display and log show the exact loaded, missing and pending totals.

A 1x image is not mandatory. If only a valid 2x or custom-resolution variant exists, the resolver uses that source. An orange entry means that no usable installed variant was found, not merely that 1x is absent.

Import Project Zomboid Tileset PNG

This function creates the minimal Project Zomboid tileset information from a PNG. It avoids requiring generic Tiled metadata that PZ does not use. The PNG must still have a valid tile-grid layout and a unique tileset name.

  1. Choose Import Project Zomboid Tileset PNG....
  2. Select the PNG and confirm the tile resolution/grid.
  3. Review the generated tileset name and image path.
  4. Save the TMX and update Tilesets.txt if the image is meant to be part of the shared catalog.

Large custom and Jumbo tiles

Custom dimensions up to 4096 are accepted by creation and pack tools. Jumbo support removes former assumptions that all packed source rectangles fit the historical small-tile bounds. Large images consume more texture memory and can reveal game-side limits that are outside the editor.

Identification, IDs and export

  • Tile palettes display the tileset name and numeric tile ID.
  • ID reconstruction/reassignment tools repair catalog order after tileset additions or changes.
  • Direct tile export writes a selected tile as a PNG to an explicit portable path.
  • Pack Extractor supports exact full-name searches and multiple prefixes, reducing unwanted matches in large packs.

Opening the Versatile Pack Extractor now shows cancellable progress while texture previews and hashes are prepared, including the current page and texture. Extraction phases are reported as files are validated and written. See PZ-Pack-Comparator-and-Extractor.md for the comparator, hash, filter, reconstruction, and output details.

TileDefs and property help

TileDefs are tile properties consumed by Project Zomboid. Many exist in Java or Lua without public mapping documentation. The current property catalog includes additional B42 definitions found by source analysis.

Open the definition for a tileset tile

Right-click a tile in the Tilesets dock and choose Edit Project Zomboid Tile Definition.... TileZed checks the ordered .tiles and .tiles.txt files configured in Preferences, opens the file that defines that tileset, and selects the exact tile index. Official files are discovered from the configured Project Zomboid installation. Custom definition files retain their configured order.

If another TileDefs file has unsaved changes, TileZed asks whether to save them before switching files. If no configured file defines the selected tileset, the warning lists the files that were checked. Add the correct file under Edit > Preferences > Tile Property Files. This command edits Project Zomboid TileDefs and does not add arbitrary metadata to the current TMX.

Hover over a property to read its English description. Descriptions explain expected value shape and likely engine use; where game behavior is inferred rather than explicit, treat the text as guidance and validate in-game.

Property and value filters help answer:

  • which tiles already use a definition;
  • which values occur in the current tileset set;
  • whether a renamed or removed property remains referenced;
  • whether IDs and definitions remain consistent after importing tiles.

Comparing definitions

The enhanced Compare .tiles Files window reports complete file SHA-256, unique tilesets, structural ID/image/grid/count differences, changed properties, and tile records found on only one side. Search and status filters can be combined. Selecting a result shows both tile images and a highlighted property table. File 2 is the merge base; structural differences are reported without being silently inserted.

Snow and replacement mappings

The Snow / Replacement Editor supports SnowTile, BurntTile, and custom mapping keys. Drag one source tile, assign it to several selected targets, or match selected targets to source tiles with the same ID. Blue overlays are resolved; red outlines identify unresolved references. See PZ-TileDef-Comparator-and-Snow-Editor.md for the complete workflow.

Automapper

This section describes the current in-integration Automapper panel.

See the dedicated Automapper rule-map reference for layer naming, indexes, map properties, tile and object matching, output alternatives, and troubleshooting.

Rule discovery

A saved target TMX first uses a nearby automapping-rules.txt. A legacy rules.txt remains compatible when it is actually an Automapper manifest. Each non-comment entry may point to a rule-map .tmx or another .txt list. Relative paths are resolved from the list containing them.

A WorldEd terrain/BMP Rules.txt contains version, alias, rule, and tile blocks. It is detected and ignored rather than interpreted as hundreds of missing Automapper paths. Create automapping-rules.txt beside the TMX when both systems are used in the same project.

  • Reload rereads lists and rule maps.
  • Apply runs all loaded rule patterns on the target map.
  • Interactive reapplies relevant rules as tiles or objects change.
  • The panel shows file paths, pattern counts, warnings and errors.

Safety checks

Recursive list inclusion is skipped with a warning. The same rule map is not loaded twice. Unsupported extensions are reported. A failed or absent manifest is not retried for every brush stroke; after correcting it, use Reload. Unsaved target maps cannot reliably resolve a neighboring manifest and are rejected explicitly.

Tile and object inputs

input and inputnot may be tile layers or Object Groups. Object patterns can compare name, type, shape, position, dimensions, polygon data and custom properties. A property value of * means “the candidate must have this property, but any value is accepted.”

Interactive automapping can produce many changes quickly. Keep Undo history visible and test a new rule set on a copy before enabling it.

Lua mapping automation

TileZed embeds Lua for editor automation. It does not run Project Zomboid gameplay scripts. Batch scripts can inspect or modify tiles, BMP data, selections, layers, Object Groups, zones and RoomDefs. Interactive Lua tools can preview placement and create one Undo command per gesture.

See the dedicated Lua scripting and API reference for:

  • current-map, directory and WorldEd-world execution modes;
  • zero-based API indexing versus one-based Lua tables;
  • all exposed Map, Layer, Tile, BMP, Object, Region and TileTool functions;
  • tile lookup, placement, deletion and replacement by exact name;
  • deferred access to whitelisted TileZed Qt actions and export dialogs;
  • RoomDefs and object-property examples;
  • interactive callbacks, preview and Undo;
  • error handling, progress and cooperative cancellation.

BuildingEd

BuildingEd now supports transactional Lua editor scripts. See the BuildingEd Lua scripting and API reference for execution, rooms, objects, user-tile layers, properties, selections, Undo behavior and examples.

Separate application

BuildingEd is launched as its own executable and uses its own red B icon. It still shares the TileZed libraries, tilesets and Building catalogs in the portable suite.

Startup progress

At startup, and after changing the Tiles directory, BuildingEd reads all available tilesets and the following catalogs:

  • BuildingFurniture.txt;
  • BuildingTemplates.txt;
  • BuildingTiles.txt;
  • TMXConfig.txt.

The progress display proves that the application is working instead of frozen. The log records loaded and missing files. A varying tileset count usually means the available PNG/catalog set changed or a file failed to load; consult the detailed log rather than relying only on the total.

Appearance and state

BuildingEd uses the same QSS theme system as TileZed. Its window, docks and internal panel splitters are stored in portable settings, including the tileset/layer panel proportions.
