TileZed Automapper

Automapper matches tile or object patterns in a working TMX and copies the corresponding output from one or more rule-map TMX files. The Automapper dock shows loaded files, target layers, pattern counts, map properties, warnings, and errors.

The mental model

Automapper does not generate a map from a script. It compares a small example map against the map being edited:

  1. The target TMX is the real map being edited.
  2. A rule-map TMX contains one or more small examples.
  3. Input_* layers describe what must already exist in the target map.
  4. InputNot_* layers describe what must not exist.
  5. Output_* layers describe what Automapper will place.
  6. A Regions layer separates the rule-map into connected patterns. Automapper slides each pattern over the target map and applies its output wherever its complete input matches.

The text manifest only establishes load order. The actual matching rules live in the referenced TMX files.

This reference describes and is checked against the Automapper implementation shipped in this TileZed build. The preferred manifest name and WorldEd-file isolation are PZTools compatibility policies; they do not change the rule-map matching format.

Smallest useful project

my-map/
  town.tmx
  automapping-rules.txt
  rules/
    grass-border.tmx

automapping-rules.txt contains:

# Load order matters.
rules/grass-border.tmx

The target town.tmx and rule map both need a tile layer named Ground. The rule map then uses these layers:

Rule-map layerWhat to paint in it
RegionsAny visible marker tile over the complete area used by the example. The marker tile itself is never copied.
Input_GroundThe ground tiles that must be present in the target map.
InputNot_GroundOptional ground tiles that reject the match.
Output_GroundThe replacement or additional ground tiles to copy to the target map.

For a first rule, paint one connected marker area in Regions, put one known tile at the same coordinate in Input_Ground, and put the desired result at that coordinate in Output_Ground. Save both maps, open View > Automapping, press Reload, inspect the rule entry, and use Apply. Once the full-map result is correct, enable Interactive if the workflow benefits from it.

The layer suffix is the target layer name, not an arbitrary rule label. Input_Ground reads target layer Ground; Output_Furniture writes target layer Furniture. Names and layer types must match.

Loading rules

Save the target map first. TileZed searches beside it for automapping-rules.txt. For compatibility, an existing rules.txt is accepted when it is an Automapper manifest. The explicit automapping-rules.txt name always wins when both files exist.

Each non-empty line that does not begin with # or // names either a rule-map .tmx or another .txt list:

# paths are relative to this list
rules/roads.tmx
rules/vegetation.txt
C:/shared-rules/signs.tmx

Relative paths are resolved against the list containing them. Nested lists are supported. Recursive includes, duplicate rule maps, missing files, and unsupported extensions are reported rather than loaded repeatedly.

WorldEd terrain/BMP files also use the name Rules.txt, but their version, alias, rule, and tile-block syntax is not an Automapper manifest. TileZed recognizes and ignores that file. It does not turn each terrain-rule line into a missing filename.

Rule-map layer names

NamePurpose
RegionsDefines both input and output extents. Each connected region is one pattern.
RegionsInputInput matching extent when it differs from output.
RegionsOutputOutput copy extent when it differs from input.
Input_TargetPositive pattern matched against tile layer or Object Group Target.
InputNot_TargetPattern that must not match Target.
Output_TargetTiles or objects copied to target layer/group Target.

Prefixes are case-insensitive. The underscore is required. The part after it is the exact target layer name and type.

Indexes and alternatives

An optional index between the prefix and underscore groups conditions and outputs:

Input1_Ground
InputNot1_Objects
Output1_Floor
Output1_Furniture

Input2_Ground
Output2_Floor

For input groups, every named target inside one index must match; matching any complete index is sufficient. Repeated Input or InputNot layers with the same index and target provide accepted or rejected alternatives.

Each distinct Output index is an alternative output group. When several exist, Automapper chooses one randomly for each match. Give layers the same output index when they must be copied together.

Rule-map properties

PropertyMeaning
DeleteTilesClears affected output areas before copying output, removing results left by an older match.
AutomappingRadiusExpands the edited region by this many tiles during interactive automapping.
NoOverlappingRulesPrevents output regions produced by the same rule from overlapping on a target layer.

Property spelling is case-insensitive. Values must convert to the required boolean or integer type. Unknown or invalid properties produce warnings.

Tile matching

  • The target cell must be inside the target layer and not empty.
  • A tile in a positive input layer accepts that exact tile.
  • A tile in an InputNot layer rejects that exact tile.
  • With only positive layers, an empty rule coordinate accepts tiles not used elsewhere by the positive pattern.
  • With positive and negative layers together, positive coordinates must match an allowed tile and no negative tile may match.

Object Group matching

Input and InputNot layers may also be Object Groups. A rule object compares its shape, translated position, dimensions, polygon data, and custom properties. Name and type are compared when their rule values are non-empty. A rule property value of * means the candidate must contain that property but its value may be anything.

All objects in a positive pattern must be found. A matching InputNot object pattern rejects the rule.

Applying and interactive mode

  • Reload rereads the manifest, nested lists, and rule TMX files.
  • Apply runs all loaded rules on the complete target map.
  • Interactive reruns relevant rules when tile regions or map objects are added, changed, or removed.

Rules run in load order. The changed region produced by one rule is passed to following rules, allowing multi-stage pipelines. Application is stored as Apply AutoMap rules in the Undo stack.

Test new rule sets on a copy. Interactive mode can trigger a large pipeline after a small edit, especially with a large AutomappingRadius or recursive output dependencies.

Working example included with the source

TileZed/examples/sewer_automap is a complete multi-stage example. Open sewers.tmx. Its manifest loads seven rule maps in order:

  1. fill the marked sewer region;
  2. choose transition tiles;
  3. place straight walls;
  4. place inner corners;
  5. place outer corners;
  6. correct ambiguous corners with InputNot_set;
  7. choose final corner stones from alternative inputs.

rule_001.tmx is the best starting point. It demonstrates Regions, Input_set, three tile outputs, an Object Group output, DeleteTiles, and AutomappingRadius. Disable later lines in the manifest and apply the maps one at a time to see how each stage changes the output.

Design and performance guidelines

  • Start with Apply and a copy of the target map. Enable interactive mode only after the complete pipeline is predictable.
  • Keep AutomappingRadius as small as the largest pattern that must react around a changed tile.
  • Put broad classification rules before detail and correction rules.
  • Avoid having a late output recreate the input of an expensive early stage unless the pipeline intentionally needs that dependency.
  • Use separate indexed outputs only for true random alternatives. Give layers the same output index when they must be applied together.
  • Use DeleteTiles only after confirming which output area is owned by the rule.

Where diagnostics appear

The Automapping dock shows the selected manifest, every loaded rule map, pattern counts, output layers, radius, properties, warnings, and errors. The same messages are written to the current TileZed log under settings/logs. A missing or invalid manifest is attempted once per document; after correcting it, press Reload. This prevents ordinary brush strokes from repeatedly parsing the same bad file.
